# Platform vision

KAREN OS is a personal AI operating system intended to help an individual think, build and manage routine work under human supervision. Its platform should become reusable without requiring the operator to publish personal context or depend on one model provider.

The intended experience supports direct conversations, hands-on engineering and bounded delegated work. A fresh compatible agent retrieves authoritative rules, project context and the task rather than relying on an earlier chat. Read-only exploration needs no task or ownership claim. Actionable work needs an explicit authorised task and applicable approvals.

Before substantial frontend or backend implementation, the operator sees a reviewable visual or technical proposal. Reusable design principles, tokens, components, templates, skills and a future Project Factory reduce repeated work. Extract reuse from proven needs rather than building a speculative service hierarchy.

A handoff records scope, revisions, checks, decisions, uncertainty and the next safe action. A recipient confirms the previous worker stopped and revalidates context, tools and authority. Shared records do not imply shared transcripts, filesystem access, credentials or tool permissions.

Morning and evening briefings, capacity monitoring, mobile review, personal operations and optional chief-of-staff or gateway integrations are future capabilities. Missing access must remain visible. Subscription limits and separately billed APIs are different resources. Additional spending needs explicit operator approval.

Level 2 means supervised, bounded autonomy here, not an external certification. Consequential communication, publishing, installation, spending, sensitive-data destinations, destructive actions and permission expansion remain approval-controlled. Privacy, recovery, least privilege and an emergency stop are design requirements.

The local context utilities are a foundation, not a functioning autonomous assistant. The public platform supplies reusable contracts; a private instance retains personal tasks, memory, preferences and operational data. Private operator policy may narrow permissions, and no retrieved file can grant new authority.

## Proposed acceptance stories

These generic stories preserve product requirements without disclosing personal projects. They are not implemented capabilities.

- An operator captures a design reference from a phone. The system prepares a proposal, compares current and proposed UI, obtains design approval, then prepares tested reusable changes and a reviewable preview. Merge, deployment and any public announcement require separate approval; a draft announcement is never automatically posted.
- An operator opens a fresh compatible coding session in an example application and explores a navigation or preview idea. The agent retrieves relevant project and device constraints, shows an appropriate design before substantial UI work, and records an issue or handoff only when discussion becomes actionable. Direct work remains usable without a chief of staff.
- An operator proposes a private media application with memories, a montage and scheduled message drafts. A future Project Factory prepares a private-by-default brief, architecture, visual proposal and cost/privacy assessment. Personal media access, repository creation, deployment and sending each need scoped authority. A public platform does not imply that every generated project is public.
- A morning briefing shows actual calendar access, priorities, blockers, approvals and resource observations. An evening review distinguishes verified, drafted, merged and blocked work, and proposes carryovers. Missing connectors are labelled unavailable; notifications are restrained and schedules require approval.
- A worker reaches a provider limit during an authorised task. It checkpoints files, tests, plan and remaining work. A compatible recipient revalidates scope, ownership, revisions and tools from durable records. No automatic billed fallback, transcript sharing or mandatory coordinator is assumed.

## Design and operating quality

Roles describe responsibilities, not one always-running process per department. Direct collaboration and bounded delegation coexist; reserve scarce capacity for hands-on work. Optimise accepted outcomes per total usage, use deterministic utilities for routine work, bound retries, and stop on repeated failures. Provider limits, reset times and API charges are distinct; observations must be labelled reported, manual, estimated, stale or unknown.

Frontend proposals should expose editable screens, responsive variants and interaction states where useful. Verify actual Figma account/tool capabilities or seek approval for a browser/component alternative; an image is not editable design layers. Backend proposals show current and proposed dependencies, request flow, failure handling, alternatives, cost and rollback. Keep diagrams with source reviews. Match design effort to risk rather than line count; design-first token savings remain a hypothesis to measure.

Build a coherent family of products while preserving platform and product differences. Reuse proven tokens, accessibility patterns, components, engineering conventions and starters; justify exceptions and avoid premature abstractions. Mobile capture, viewing, execution and deployment are separate permissions. A sleeping or disconnected workstation cannot be assumed to continue local jobs. Reconcile uncertain external actions before retrying to avoid duplicates.

Before significant work, explain the user friction, supporting requirements and unresolved proposals, smallest viable change, existing reusable assets, reviewable design, affected data/services/permissions/cost, rollback, approval gates, verification, handoff and stop criteria. Reviewers inspect actual artefacts and return targeted findings. A recommendation, newer file or commit is not operator acceptance. Simplify if the system adds more management work than useful outcomes.
